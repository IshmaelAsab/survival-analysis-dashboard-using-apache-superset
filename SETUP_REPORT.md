## Issues and Fixes

### 1. `git clone` timed out but the repository actually finished cloning

- Symptom: the first `git clone https://github.com/apache/superset` call hit the tool timeout.
- Diagnosis: the `superset` directory and `.git` metadata were present afterward.
- Fix: I inspected the partially completed clone instead of recloning and continued from the existing checkout.

### 2. Git reported "dubious ownership" for the cloned repo

- Symptom: `git rev-parse --is-inside-work-tree` failed because the repo owner was `hp` while the Codex shell token was `CodexSandboxOffline`.
- Fix: I used `git -c safe.directory=C:/Users/hp/Documents/GitHub/Apache-Superset/superset ...` for subsequent git commands instead of modifying tracked repo content.

### 3. Docker Desktop install command reported `NET LOCALGROUP` syntax errors

- Symptom: the Docker installer run ended with syntax output from `NET LOCALGROUP`.
- Diagnosis: the Docker installer itself succeeded; only my follow-up user-add command had quoting issues.
- Fix: I verified Docker directly after the install and continued because Docker Desktop, Docker CLI, Docker Compose, and the Windows Docker service were all present and working.

### 4. Non-elevated Docker access failed for the Codex shell

- Symptom: `docker info` from the normal shell returned `permission denied while trying to connect to the docker API at npipe:////./pipe/docker_engine`.
- Related warning: Docker CLI also tried to read `C:\Users\hp\.docker\config.json` and hit `Access is denied`.
- Diagnosis: the sandbox token and its environment did not align with the desktop user profile, even though the desktop user `hp` was in `docker-users`.
- Fix: I ran Docker commands with elevation for the setup itself and set `DOCKER_CONFIG` to a temp directory (`$env:TEMP\codex-docker-config`) for the elevated Docker commands.

### 5. `/health` failed on the first request

- Symptom: the first health check returned `The underlying connection was closed: The connection was closed unexpectedly.`
- Diagnosis: `superset_app` was still finishing its first boot sequence after `superset_init` exited.
- Fix: I checked the logs, waited, and retried until `http://localhost:8088/health` returned `OK`.

### 6. SQL Server virtual datasets failed when they ended with `ORDER BY`

- Symptom: the first pass of the survival-analysis helper failed when Superset queried some SQLBook virtual datasets.
- Diagnosis: Superset wraps virtual dataset SQL in an outer query, and SQL Server rejects a trailing `ORDER BY` inside that subquery unless it is paired with `TOP`, `OFFSET`, or XML.
- Fix: I removed the trailing `ORDER BY` clauses from the milestone, market summary, and revenue dataset SQL and let the saved chart configuration handle display ordering instead.

### 7. REST-created charts needed saved `query_context` values for reliable warmup

- Symptom: the dashboard objects were created, but validation was incomplete because several saved charts did not have persisted `query_context` payloads.
- Diagnosis: the chart create/update flow stored chart parameters, but not every chart had the saved query-context blob that Superset's warmup path expects.
- Fix: I updated the local helper to backfill `query_context` for the non-legacy charts and reran the helper until every SQLBook survival chart warmed successfully.
